## 现象

`dev/wiki_maintain.py` 生成的蒸馏摘要，头部写着：

```
- 上限：失败簇 ≤5，成功簇 ≤3，单条 ≤15000 字符
```

其中前两条（簇数）是真的被 `[:max_fail]` / `[:max_succ]` 执行了；
**第三条「单条 ≤15000 字符」从来没在单条上生效过**——`_truncate()` 全文件
只有一次调用，在 `return` 之前：

```python
return _truncate(text, BRIEF_ITEM_MAX_CHARS * 12), ...
```

截的是**整篇**（180,000 字符），不是**每条**（15,000 字符）。单条想超就超，
而摘要头部照样写着它没超。

实测：往 `params` 里塞 25,000 字符的自由文本，单条失败簇长到 14,161 字符
仍在限内——不是因为守住了，是因为 `params` 目前只有 8 个标量，凑不够。
**这是潜伏缺陷，不是现网故障**：一旦有人把 `--title` 之类自由文本记进
`params`，它会静默破界，且没人会收到任何信号。

## 机制

这不是"忘了写上界"（那是 `p08`），而是**上界写在了错误的层级**：

1. **常量名暗示了粒度**：`BRIEF_ITEM_MAX_CHARS` 里就写着 `ITEM`。
   名字对，调用错。读代码时名字会替作者背书，读者不会去核对调用点在哪一层。
2. **N×上限 看起来像"更宽松的兜底"**：写 `* 12` 的人（我）当时的想法是
   "8 条 × 每条 15000，再留点余量"。这个推理是错的——整篇兜底**不能**
   推出每条受限，两者是正交的。整篇 180,000 的上界在单条 200,000 时依然满足。
3. **既不报错也不告警**：截断是"静默降级"，超限的那一刀砍下去没有任何痕迹
   （本例里连痕迹都没有，因为那一刀根本没落在单条上）。

与 `p08` 的关系：p08 是"**有常量、无调用点**"，本条是"**有调用点、
但粒度错了**"。共同点是**声明与行为可以长期不一致且零报错**，所以两者都
只能靠"逐条核对自称的约束"发现，不能靠跑测试——测试当时是全绿的。

## 处置

1. 长字段**先各截一刀**（`params` 的 JSON 截到 2000），保住条目结构——
   否则整条截断会把末尾那句"**待回答**：这是环境问题、代码问题，还是文档
   /默认值问题？"砍掉，而那句才是蒸馏摘要里唯一可操作的部分。
2. 每条拼完后**再过一次 `_truncate`**，作为兜底。
3. 整篇那刀保留，但注释写明它防的是头部/环境警告段失控，**不是**用来
   代替每条上限。
4. selftest 钉 4 条断言：极端输入下单条不超限、超限时长字段被截（出现
   `…[已达单条` 标记）、截断后"待回答"还在、源码里每条都过 `_truncate`。

## 判据

```python
recs = [一条 params 里塞 25000 字符、stderr_tail 3000 字符的轨迹]
text, nf, ns = build_brief(recs)
max(len(b) for b in text.split("### [") if b.strip()) <= BRIEF_ITEM_MAX_CHARS
```

修复前：整篇兜底存在，单条可超限，断言不存在所以无人知晓。
修复后：极端输入下单条 5,247 字符，且"待回答"行完整。

## 横向用法

写"上限 / 限额 / 配额"时，除了 `p08` 那句"谁来执行它"，还要再问一句：
**它作用在哪个粒度上？** 常见的错配形态：

- 每条的限额，实现成整批的限额（本条）
- 每次调用的限额，实现成整个进程的限额
- 每文件的限额，实现成整个目录的限额

判据很简单：**把 N 取成 1（或 2），看这个上界还成不成立。** 如果 N=1 时
上界形同虚设，那它的粒度就是错的。
